Before you write code

What is Bioconductor?

  • A repository of open-source R packages for analysing and understanding high-throughput biological data
  • > 2,300 software packages, plus annotation and experiment data packages
  • Two releases per year (~April and ~October), each tied to an R version
  • A community: developers, reviewers, support site, Zulip chat, conferences


Packages are reviewed before acceptance and built and checked nightly on Linux, macOS and Windows.

Is my package in scope?

Bioconductor packages should address the analysis of high-throughput biological data: sequencing, microarrays, flow cytometry, mass spectrometry, imaging, single-cell, etc.


Core principles:

  • Interoperability: reuse Bioconductor data structures and infrastructure
  • Best practices: complete documentation, executed vignettes, unit tests
  • Commitment to maintaining the package and answering user questions

Choosing biocViews

  • Browse the hierarchy at bioconductor.org/packages/release/BiocViews.html
  • Pick at least two leaf terms (the most specific ones) from the same trunk
  • Terms are case-sensitive, and must be on a single comma-separated line

What makes a good package?

Integration with the ecosystem

  • Interoperability: take and return Bioconductor classes
  • Don’t reinvent the wheel: reuse existing import functions, classes and methods
  • Lightweight: as few dependencies as possible
  • Tested and documented

Small, focused functions

  • Each function does one thing (split anything longer than a screen)
  • A consistent API: similar argument names across functions, camelCase or snake_case.
  • Few exported functions that users actually need; helpers stay internal (.helperName())

A typical development workflow

# Step 1: Create the skeleton of a new package
usethis::create_package("~/Documents/toyBioc")

# Step 2: Add Bioconductor-style files with biocthis
biocthis::use_bioc_description()        # DESCRIPTION with biocViews etc.
biocthis::use_bioc_vignette("toyBioc")  # vignette template with BiocStyle
biocthis::use_bioc_github_action()      # GitHub Actions to check the package

## Step 3: Write code and tests
usethis::use_r("normalizeCounts")       # creates R/normalizeCounts.R
usethis::use_test("normalizeCounts")    # creates tests/testthat/test-normalizeCounts.R

## The development loop: repeat until happy
devtools::load_all()                    # load the package (like library())
devtools::document()                    # update man/ and NAMESPACE
devtools::test()                        # run unit tests
devtools::check()                       # run R CMD check

Mind the number of dependencies

Dependencies can break and/or make package installation slower.

Before adding a dependency, ask yourself:

  • Do I need the whole package for one small function?
  • Is the function used in the core of my package, or in a niche feature?

Move niche dependencies to Suggests

A heavy package used only in one rarely-used function can go to Suggests.

plotDensities <- function(se) {
    if (!requireNamespace("ggplot2", quietly = TRUE)) {
        stop("Package 'ggplot2' is required for this function. ",
             "Install it with BiocManager::install('ggplot2').")
    }
    df <- .longFormat(se)
    ggplot2::ggplot(df, ggplot2::aes(x = value, colour = sample)) +
        ggplot2::geom_density()
}


💡 Use pkg::fun() for packages in Suggests. Don’t import them in NAMESPACE.

DESCRIPTION: License

  • Bioconductor packages must be open-source: use a standard license and give its version
    • GPL-3, GPL-2, Artistic-2.0 (common in core packages), MIT + file LICENSE, …
  • Licenses that restrict use are not suitable:
    • CC BY-NC 4.0, CC BY-NC-SA 4.0, CC BY-NC-ND 4.0 (no commercial use), ACM
  • Check that your license is compatible with the licenses of your dependencies (and of any third-party code you include)

R/: what a function looks like

normalizeCounts <- function(counts, method = c("cpm", "log2cpm")) {
    method <- match.arg(method)
    .checkCounts(counts)

    libsize <- colSums(counts)
    cpm <- t(t(counts) / libsize) * 1e6

    if (method == "log2cpm") {
        cpm <- log2(cpm + 1)
    }

    return(cpm)
}
  • Validate inputs early (here, in the internal helper .checkCounts())
  • 4 spaces of indentation, ≤ 80 characters per line, <- for assignment

Code: some do’s and don’ts

# Bad 1: if `x` is empty
lapply(1:length(x), ...)

# Bad 2: type not explicit
res <- sapply(x, mean)

# Bad 3: 2+ classes, inheritance
if(class(se) == "SummarizedExperiment")

# Bad 4: `T` can be a variable
normalizeCounts(counts, log = T)

# Bad 5: `cat()` cannot be silenced
cat("Normalizing", n, "samples...\n")

# Bad 6: `set.seed()` inside code 
set.seed(123)
idx <- sample(ncol(counts), 10)
# Good 1: empty sequence with empty `x`
lapply(seq_along(x), ...)

# Good 2: explicit type
res <- vapply(x, mean, numeric(1))

# Good 3: inheritance handled
if(is(se, "SummarizedExperiment"))

# Good 4: `TRUE` or `FALSE
normalizeCounts(counts, log = TRUE)

# Good 5: `message()`/`warning()`/`stop()`
message("Normalizing ", n, " samples...")

# Good 6: let users set the seed
idx <- sample(ncol(counts), 10)

tests/: write tests right after the code

Tests check if your functions work as expected, and should be written early.

usethis::use_r("normalizeCounts")     # 1. write the function in R/
usethis::use_test("normalizeCounts")  # 2. write its tests, right away
devtools::load_all()                  # 3. load the package...
devtools::test()                      #    ...run the tests, and repeat

Advantages of writing tests early:

  • You still remember the edge cases you had in mind while writing the code
  • Bugs are caught early, when they’re easy to fix
  • You can refactor later with confidence: tests tell you if you broke something
  • Tests document how the function is supposed to behave

tests/: good testing practices

Use toy data sets

  • Small objects created in the test file or in tests/testthat/helper-*.R
  • Or small example data that ships with the package (data/, inst/extdata/)
  • Tests should run in seconds

Avoid over-testing

  • Test behaviour (inputs → outputs), not implementation details
  • Don’t test other packages’ functions
  • Avoid many near-duplicate tests
  • 100% coverage is not a goal in itself

src/: do you really need it?

src/ is optional. Most Bioconductor packages are written in pure R.

Cost of compiled code:

  • Users (and Bioconductor’s build machines) need compilers and system libraries on Linux, macOS and Windows
  • Builds can fail on one platform only, and memory errors (segfaults) are hard to debug
  • Fewer people can review, contribute to, and maintain the code

src/: do you really need it? (cont’d)

Only add compiled code in the (rare) cases where well-written R code is still too slow, and you have measured that it is. The workflow:

  1. Write correct R code, with tests
  2. Profile it to find the bottleneck
  3. Optimise the bottleneck in R, and benchmark the alternatives
  4. Still too slow? Only then rewrite that bottleneck in C++ or Rust

Benchmark: compare alternatives

Once you’ve found the bottleneck, compare alternative implementations with bench:

m <- matrix(rnorm(1e5 * 10), ncol = 10)   # 100,000 genes x 10 samples
colSumsLoop <- function(x) {
    out <- c()
    for (j in seq_len(ncol(x))) {
        s <- 0
        for (i in seq_len(nrow(x))) s <- s + x[i, j]
        out <- c(out, s)
    }
    out
}
bench::mark(
    loop = colSumsLoop(m), apply = apply(m, 2, sum), colSums = colSums(m),
    iterations = 20
)[, c("expression", "min", "median", "mem_alloc")]

src/: C++ code with Rcpp

For bottlenecks that can’t be solved in R, write C++ code with Rcpp:

Rcpp::cppFunction("
NumericVector colSumsCpp(NumericMatrix x) {
    int nc = x.ncol();
    NumericVector out(nc);
    for (int j = 0; j < nc; j++) {
        out[j] = sum(x(_, j));
    }
    return out;
}")

colSumsCpp(matrix(1:6, nrow = 2))
#> [1]  3  7 11

Vignettes: a vignette is teaching material

  • Put text before and after every chunk: what is the code going to do? How should the output be interpreted?
  • Execute all chunks. Static vignettes (eval = FALSE everywhere) are not accepted
  • Use small example data. The goal is to show how to use the package, not to reproduce a paper’s results
  • Don’t assume prior knowledge: explain the data, the classes and the biology
  • Show a complete workflow that users can copy and adapt

Checking and submitting

R CMD check vs BiocCheck

R CMD check BiocCheck
Check R package requirements: installs, examples run, tests pass, docs match code, … Bioconductor guidelines: biocViews, version number, vignette, coding practices, formatting, …
Run with devtools::check() BiocCheck::BiocCheck()
Examples of issues Undocumented arguments, undeclared dependencies, failing tests sapply(), 1:n, lines > 80 chars, \dontrun{}, missing sessionInfo() in vignette

Your package must pass R CMD check and BiocCheck with 0 errors and 0 warnings. Fix NOTEs too, or justify them to the reviewer.

Running the checks

## In the package directory
devtools::check()                              # R CMD build + R CMD check

## On the package source
BiocCheck::BiocCheck()


Limits to keep in mind:

  • R CMD check must take less than 10 minutes
  • Package tarball < 10 MB. Individual files ≤ 5 MB
  • Vignettes, examples and tests should use < 8 GB of memory
  • Develop and test with the devel version of Bioconductor

The submission process

Since 2026, submissions go through Bioconductor/BiocContributions, with builds and checks run by rOpenSci’s R-universe (GitHub Actions).

Each step is shown as a label on your GitHub issue (precheck-passed, pre-review, Build OK / Build Error, review in progress, package accepted, …).

Submitting, step by step

  1. Put your package in a public GitHub repository named exactly like the package
  2. Open an issue at BiocContributions using the new submission template, with your repository’s URL
  3. An automatic precheck looks at DESCRIPTION (version x.99.y, biocViews, no Remotes:), vignettes/ and file sizes
  4. Read the policies posted in the issue and comment /accept-policies
  5. Your repository is copied to the BiocStaging organisation and added to an R-universe. From now on, push changes there
  6. Bump the version (0.99.0 → 0.99.1) with each push to trigger a new build. Build reports are posted in the issue

The review

  • A reviewer is assigned once there are no build ERRORs (justify any remaining WARNINGs or NOTEs in a comment). Label: review in progress
  • Reviewers are volunteers who go through your code, docs and vignette against the guidelines
  • Reviews usually start within ~3 weeks of a clean build, and may take several rounds
  • If a review stalls and you don’t reply, the package may be marked as inactive review and the issue closed

The review (cont’d)

Tips:

  • Respond to every comment in the issue, point by point (what you changed, or why you didn’t)
  • Push all fixes (with a version bump), then comment on the issue
  • Think of it as free code review from experienced developers.

Maintaining a package

After acceptance

  • Your package is moved to Bioconductor devel, and you get a BiocCredentials account to manage the SSH keys for push access
  • It goes into the next release (April or October)
  • Each release creates a release branch (bug fixes only) and you keep developing on devel (new features)
  • Version numbers: x.y.z, with even y in release and odd y in devel (e.g., 1.2.0 in release, 1.3.0 in devel). Bump z with every change you push

Being a maintainer

  • Check the nightly build reports and fix errors and warnings quickly (failures are sent from BBS-noreply@bioconductor.org)
  • Answer questions on the support site (add your package to your Watched Tags)
  • Subscribe to the bioc-devel mailing list
  • Keep the maintainer email in DESCRIPTION up to date
  • To remove functions, follow the deprecation guidelines (.Deprecated() → .Defunct() across releases)
